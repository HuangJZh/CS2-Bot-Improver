## 瞄准与开火：确实读到了什么

### 原生 Profile 的误差控制

当前游戏自带文件的 Elite 模板为 Skill=100、ReactionTime=0.05、AimFocusInitial=0.5、AimFocusDecay=0.1、AimFocusOffsetScale=0.05、AimfocusInterval=0.05；Expert 模板 ReactionTime=0.20。

这些只是模板字段，不能认定 Aim Rush 中每个 Bot 都使用 Elite，也不能把 50ms 当成从视觉出现到实际出弹的总耗时。需要实例模板与开火记录验证。

其设计把初始偏差、误差收敛、跟踪偏差和更新间隔分开。我们的难度包基本清除了原生 AimFocus 偏差，再由 HumanAimModel / VisualLocalization 添加误差。直接叠回原生误差会形成两套误差来源；应对照选择一套主控制，而不是继续叠加。

### 当前 CS2 自带攻击模块的接口

`scripts/ai/modules/bt_attack.kv3` 可读链路为：

```
短期攻击记忆 → 反应时间筛选 → 距离评分选 Enemy
  → 装备选择 / 交战走位 / 瞄准 / 攻击并行更新
  → action_aim 产生 AimReady
  → action_attack 消费同一个 AimReady，输出 Attacking
  → action_combat_positioning 读取 Attacking
```

同一模块还区分空弹、刀具追击和区域伤害规避。AimReady 和 Attacking 将瞄准、开火、走位串起来，值得借鉴其状态分工。action_combat_positioning 的内部算法仍在引擎里，不能从这一文件推出精确横移速度、急停概率或补枪判断。

`EngagedEntities` 被写入约 1 秒的标记。所提取模块中没有看到它的跨 Bot 消费链，因此不能把这个名字当成团队共享目标或集中火力的证明。

`bt_config.kv3` 将目标获取、跟踪、瞄准就绪阈值、后坐力响应、蹲伏和不同武器的攻击持续/间隔分开配置。不过这些配置只有相应树启用时才有意义，不能将 rush 中的反应值算到 Aim Rush 的实际接敌耗时里。

### 我们值得进一步检查的地方

- 目前 BurstCadence 的主要分段长度和暂停来自难度 Profile，缺少明确的“武器 × 距离”组合策略。近距离连续压制和远距离短点射值得分别测量。
- 当前 Default 攻击转向刚度为 500，原生 Default 为 150，阻尼均为 30；普通转向刚度/阻尼也不同。参数变化会改变动态响应，不能仅认为刚度越高越好；需用实际角度轨迹验证是否产生回摆，不能据此直接认定某次抖动的根因。
- 原生字段 IsAttacking、瞄准意图和 weapon_fire 实际事件不应视为完全相同。我们还会在 IsAimingAtEnemy 时手动设置 IsAttacking；检查走位和支援逻辑时应区分“准备交战”“允许开火”和“确实出弹”，不能只盯一个布尔值。

## Bot 联动：已有证据与不能确认的部分

Aim Rush 原版没有发现自己的目标共享、队长/补枪手分工或同步出枪脚本。多人一起冲向玩家也可能是共同看见/听见同一目标、相同目标任务和短距离路径造成的，不能直接证明在共享视野。

当前 CS2 Schema 存在 IsFollowing、FollowTimestamp、AllowAutoFollowTime、IsFriendInTheWay、IsWaitingBehindFriend、PoliteTimer 等原生字段，说明可观察这些状态入口，但字段存在本身不能证明其完整运行机制。

历史原生 Bot 讲义明确介绍了跟随领队、随领队步行/奔跑、领队停下时就近掩护，以及对队友发现敌人、求援、开火和阵亡作出反应。这是可借鉴的设计方向，尚未证明 CS2 原封不动继承全部细节。

### 我们现有覆盖里的具体线索

1. `BotState.Behavior.cs` 每 tick 清除 IsWaitingBehindFriend 并重置 PoliteTimer。这可能干扰原生礼让、排队和窄口推进；这是已确认的覆盖操作，实际影响仍需单因素对照。
2. 配置显式设置 bot_auto_follow=0。需要核对其当前实际语义和生效范围，不能因此直接声称所有 Bot 对 Bot 跟随都被关闭。
3. 现有 TeamSupport 是受击/阵亡后的临时支援：每队最多一名，任务约 2.5 秒，按附近短路线靠近队友原位置。它没有持续的双人编组、领队跟随、侧向掩护位、第二人拉出的时差和相同射线的补枪窗口。
4. 支援条件会避开正在攻击、可见敌人和队友阻挡等状态，因此原生字段被其他模块改写时也可能影响支援候选。不能仅提高 Teamwork 数值来替代实际协作机制。

## 下一步最有价值的验证

- **瞄准射击**：相同武器、距离、视角和目标运动，对比原生、只改变难度参数、完整拟人控制。记录看到目标、开始转动、实际视角到位、AimReady/自定义许可、真实出弹；分别测首发和补射。
- **共享信息**：让 A 能看到安静目标，B 被遮挡且没有目标声音，先禁止 A 开枪；对比 B 的注意力、目标记忆与路线是否变化。不能把双方都听见枪声后的集火算成共享视野。
- **补枪**：固定两名 Bot 的出入口和初始间距，记录 A 首次接敌/阵亡至 B 获得合法射线并出弹的时间，比较“无信息”“队友开火”“队友受击/阵亡”条件。
- **礼让覆盖**：仅取消强制清除等待/礼让状态，与保持原样对照；不同时改变瞄准与难度，才能判断是否确实改善拥堵和跟进。

本地 `cfg/gamemode_custom.cfg` 还会 exec `my_bot_normal_config.cfg`，这份配置包含我们的 Bot 设置。测试原版不仅要隔离插件，也需要排除这条配置入口；实际是否执行及行为树是否启用，必须通过该次对局的运行时状态确认。

## 结论

瞄准射击应重点借鉴单一误差来源、明确的瞄准就绪接口、武器/距离分开的射击策略；联动应先检验原生跟随和礼让是否被覆盖，再增加持续的领队/补枪手关系。尚无证据表明原版 Aim Rush 有一套可以直接搬过来的自定义团队 AI。本轮只进行源码与接口审查，安装仍为 8.46。
