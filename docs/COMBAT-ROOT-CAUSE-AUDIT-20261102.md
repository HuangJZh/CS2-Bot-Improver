# 瞄准、连续交火与补枪检查（8.42）

日期：2026-11-02。源版本：`a1e051ed9f283ea14bd123efe0899acd96059d78`。

结论：继续统一缩短反应参数，无法修复目前的交战状态衔接。已复现旧甩枪终点造成横移目标额外修正，也观察到首枪发生在模型 perception 阶段、随后进入反应禁火的时序问题。团队补枪则没有专门实现，不能期待路径分流自动产生配合。

## 1. 高优先级：首枪接管与随后禁火衔接不一致

相关：`BotAimImprover.NativePhases.cs`、`BotAimImprover.FireGuard.cs`、`BotAimImprover.Human.cs`。

模型依赖原生先确定 Enemy，随后在 UpdateLookAngles 前构建观测与计划；禁火保护还在 tick、Update 前后、equip 等位置更新。没有计划或没有有效上下文时回交原生，这是以前避免 Bot 长时间哑火的保护。

此次 244 次开火回调中，49 次记录为 `no-observation`/perception，全部被标记为新一轮的第一枪；49 次在其后 300ms 内都出现过禁火记录。一个无烟 AK 接触例子：首枪回调时间 42.96875；随后 tick 进入 reaction，再进入 alignment/correction；下一枪回调在 234.375ms 后。

因此，实际存在“先出一枪，随后重新等待反应与定位”的控制衔接。这个顺序会破坏步枪的连续交火，尤其首枪未解决敌人时。不能把模型的 109ms 基础 Reaction 理解为所有首枪均受同一条流程控制。

边界：回调快照不是子弹发射时的原始 usercmd，不能从 `no-observation` 字符串单独断定是哪一个原生函数已经提交 Attack，也不能把四次 `burst-pause` 回调直接认定为禁火失效。需要补充 Attack 提交前后记录来定位准确接管边界。修复应是统一接管时机和“本交战已经开过枪”的状态，保留有界失效回交；不能重新使用无限期禁火。

## 2. 已确定并复现：甩枪终点提前冻结，横移目标被迫追加修正

相关：`HumanAimModel.cs` 的首次 `_planned` 分支及 `now-_start>.08f`。

首次延迟观测到达时，代码同时确定反应结束时间和 `_endView`。在等待反应结束期间，新的观测进入模型，但这个终点没有刷新。动作开始 80ms 后才允许缓慢调整终点；Mid 小幅甩枪经常在 80ms 以内结束，因此整段甩枪仍指向等待前的位置。

结果是：目标在 Bot 的反应等待期间移动，Bot 仍先去旧位置，随后再补一段跟踪/修正。误差大于 2.5° 时还会额外等待一次 SensorDelay。

生产模型复现：距离前方平面 600 单位，目标横移 250 单位/秒；128Hz 模拟、128 个种子，使用当前 Mid profile；直接输入精确可见采样，保留模型延迟和运动误差，排除视觉定位噪声与引擎执行。

| 初始角差 | 静止目标：首次模型许可中位数 | 横移目标：首次模型许可中位数 |
| --- | ---: | ---: |
| 0° | 93.75ms | 195.31ms |
| 10° | 195.31ms | 281.25ms |
| 25° | 226.56ms | 296.88ms |

横移案例在首次许可前的 correction 等待中位数为 39.06ms。

隔离实验只在临时模型副本中将终点更新延续至动作开始，其他参数不变：0° 横移案例降至 125ms，10° 降至 265.63ms，25° 降至 281.25ms。静止案例不变。这证明冻结时机确实产生额外等待，但不证明简单更新终点已解决所有移动目标问题；实验并未安装。

应在真正发动动作时，用那时已经到达的延迟观测规划运动终点；动作启动后再遵守开环/有限反馈约束。不要让 Bot 获得当前隐藏坐标。

## 3. 高优先级设计缺口：没有持续的交战和快速换目标状态

相关：`BotAimImprover.Human.cs` 的 state 创建条件。

Enemy 或武器句柄变化时，会销毁整个 HumanState，再创建一个 HumanAimModel。反应、视觉队列、运动状态、连射计数和首枪准备均从头开始。当前短暂丢失同一目标的记忆保留，并不覆盖“旧目标死去、立即打旁边第二人”。

重新观察新目标是合理的，但对已经在视野内的第二人，不应该无条件按完全未知的新接敌重新执行整段流程；同一 Bot 的开火历史和后坐力背景也不应因换 Enemy 而凭空消失。

本次 tick 记录到 5 次连续可见过程中的目标切换；同目标计划起始时间变化的检测未发现反复重建。因此当前证据不支持“每个 tick 都重置反应”，问题集中于真正换目标/换武器的边界。

## 4. 明确缺失：团队补枪没有专门实现

相关：`BotAimImprover.Navigation.cs`、`BotAimImprover.Tactics.cs`、听觉及死亡事件处理。

现在有开局分路、站位分配、碰撞间距、声音转向、上一回合空间反馈。路径控制一旦遇到可见敌人、正在攻击或受击状态，就让原生接管。这是避免全局路线打断交火的保护，但后面没有补枪角色接续：

- 没有指定谁跟随第一接触者、以什么距离和时差接触同一射线。
- 没有基于队友接敌/死亡信息创建限时补枪任务。
- 没有检查同伴能否在队友被击杀后的短时间内获得同一敌人的合法视线。

原生 Bot 仍可能自行帮助队友，不能说完全不会补枪；但自定义层没有保证这种行为。声音提示也不是团队补枪：每人独立转向，不会自动得到合理的掩体出口、身位和协同时机。

这能解释为什么枪法参数上涨后，人仍能逐个处理 Bot。后续应在可得信息内给一名附近队友分配短期支援任务，保留目标任务优先级，避免五人一起追尸体或获取凶手的隐藏实时位置。

## 5. 已确认的架构限制：模型角度还经过原生转向，纯模型速度不是实际速度

相关：`WriteModelSpot`、`AimExecutionController`、`HumanFireDecision`、botprofile 的 LookAngle 系列参数。

正式配置没有开启 DirectViewControl。模型先生成平滑角度，再把角度变成虚拟 TargetSpot，由原生 UpdateLookAngles 继续处理；首枪再检查实际视角能否跟上。模型平滑、原生转向与有界执行反馈共同决定真实过程，单独将模型 MaxSpeed 提高 10% 不保证实际视角快 10%。

本次模型允许射击的可见 tick 中，实际 EyeAngles 与模型角度偏差中位数约 1.26°；80 个可见 tick 处于 waiting-for-execution，4 个处于 execution-settle-timeout。说明执行层确实存在差距，但并非所有接触都等满 90.9ms 的 Mid 上限。

EyeAngles 含后坐力等影响，不能把该角差当作真实子弹偏离目标的角度。当前证据不足以断言压枪向上/向下补偿符号错误，也不能据此直接开启 SetEyeAngles 或加倍压枪。

## 6. 已确认的简化方案限制：射后归零不能改善首发运动散布

相关：`BotSupport.cs` 的 OnFire。

当前概率归零水平速度发生在 weapon_fire 之后。这是之前明确选择的简化方案，能影响后续子弹，但对已经打出去的那一枪没有帮助。开枪回调里测到速度 0 也不能证明发射前已静止，因为回调前后可能已经执行归零。

真正检查首发精度需要在攻击提交之前记录速度、地面状态、武器精度和开火资格。若改为发射前制动，应继续保留武器/距离策略，不能所有枪一律停住。

## 低优先级兼容项

`BotState.Behavior.cs` 每 tick 强制 `IsEnemySniperVisible=true` 并持续刷新其 timer，即使对面拿步枪也如此。这会向原生交战逻辑提供不实的狙击威胁状态，属于需要清理的旧行为覆盖。尚未通过单因素实机对比证明它对本局强弱的影响，不能列为已经确认的主要根因。

Mixed 选头和选胸仍存在，未发现把所有目标强制改成身体的配置错误。截图敌方估算约 19/29 爆头击杀，约 66%；当前小样本独立测试则只有 4/19，两者场景不同。不能继续以更高选头概率弥补流程问题，也不能把模型选头概率当成最终爆头率。

## 建议修复顺序

1. 补充 Attack 提交时序记录，修复首枪接管及首枪后再进入 reaction 的状态错序，验证步枪首发与第二发之间没有额外禁火空档。
2. 修复动作开始前冻结终点，增加横移、急停换向、预瞄目标进入准星的回归场景。
3. 将持枪者的开火/运动连续状态与具体 Enemy 的观察状态分开，设计有视野依据的快速转移目标。
4. 加入一名同伴的限时支援/补枪任务，测试合法视线、距离、时间和目标任务冲突。
5. 在原始攻击时序和弹道方向证据充分后，再校准原生转向、首枪制动与压枪。最后才调整三档数值。

验收应同时覆盖静止/横移/反向/两名敌人/队友先接触/烟闪/换弹，不以单局比分、纯模型 185 项通过或回调视角角差替代实战验证。
